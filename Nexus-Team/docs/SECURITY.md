## Security Overview

NexusTeam implements enterprise-grade security features to protect user data, prevent attacks, and ensure system integrity. The security architecture follows defense-in-depth principles with multiple layers of protection.

### Security Principles

1. **Defense in Depth**: Multiple security layers
2. **Least Privilege**: Minimal required permissions
3. **Secure by Default**: Secure configuration out of the box
4. **Fail Securely**: Secure failure modes
5. **Complete Mediation**: All access checked
6. **Open Design**: Security through implementation, not obscurity
7. **Psychological Acceptability**: Security that doesn't hinder usability

## Authentication

### JWT (JSON Web Tokens)

NexusTeam uses JWT for stateless authentication, allowing horizontal scaling without session state.

**Token Structure**:
```json
{
  "sub": "user_id",
  "username": "john.doe",
  "email": "john@example.com",
  "jti": "token_unique_id",
  "iat": 1234567890,
  "exp": 1234571490
}
```

**Token Lifetime**:
- Access Token: 60 minutes (configurable)
- Refresh Token: 7 days (configurable)

**Token Storage**:
- **Client**: Encrypted storage using LiteDB
- **Server**: Blacklist in Redis for revoked tokens

**Token Validation**:
- Signature verification using HMAC-SHA256
- Expiration time validation
- Issuer and audience validation
- Token blacklist check

**Refresh Token Strategy**:
- Refresh tokens stored in Redis with TTL
- Single-use refresh tokens (rotated on use)
- Revocation support for compromised tokens

### Authentication Flow

1. User submits credentials (username/email + password)
2. Server validates credentials against database
3. Server generates JWT access token and refresh token
4. Tokens returned to client
5. Client stores tokens securely
6. Client includes access token in Authorization header
7. Server validates token on each request
8. Client refreshes token before expiration

### Security Features

- **Token Blacklisting**: Revoked tokens stored in Redis
- **Token Rotation**: Refresh tokens rotated on use
- **Secure Storage**: Client-side encryption for tokens
- **HTTPS Required**: Tokens transmitted over encrypted connections (production)

## Authorization

### Current Implementation

**Resource-Based Authorization**:
- Users can only access their own profile data
- Users must be chat participants to access chat/messages
- Message authors can edit/delete their own messages
- Chat creators can manage participants
- Chat owners can delete chats

### Authorization Checks

**User Profile Access**:
```csharp
// Users can only access their own profile
if (userId != currentUserId)
{
    return Forbid();
}
```

**Chat Access**:
```csharp
// Users must be chat participants
if (!await IsChatParticipant(chatId, userId))
{
    return Forbid();
}
```

**Message Operations**:
```csharp
// Only message author can edit/delete
if (message.SenderId != userId && !IsChatOwner(chatId, userId))
{
    return Forbid();
}
```

### Future Enhancements

- Role-based access control (RBAC)
- Permission-based authorization
- Admin roles and privileges
- Chat moderation capabilities

## Password Security

### BCrypt Hashing

NexusTeam uses BCrypt for password hashing, providing strong protection against rainbow table attacks.

**Configuration**:
```json
{
  "Bcrypt": {
    "WorkFactor": 11
  }
}
```

**Work Factor**: 11 (2^11 = 2048 iterations)
- Higher work factor = more secure but slower
- Recommended: 10-12 for most applications
- Adjustable based on performance requirements

### Password Requirements

**Validation Rules**:
- Minimum 8 characters
- Must contain uppercase letter
- Must contain lowercase letter
- Must contain digit
- Must contain special character
- Not in common password list

**Implementation**:
```csharp
// Password hashing
var hashedPassword = BCrypt.Net.BCrypt.HashPassword(password, workFactor: 11);

// Password verification
var isValid = BCrypt.Net.BCrypt.Verify(password, hashedPassword);
```

### Password Storage

- **Never stored in plain text**
- Only hashed passwords stored in database
- Salt automatically generated by BCrypt
- Each password has unique salt

### Password Reset (Future)

- Secure token-based reset flow
- Time-limited reset tokens
- Email verification required

## Input Validation

### FluentValidation

NexusTeam uses FluentValidation for comprehensive input validation on all API endpoints.

**Validators Implemented**:

1. **RegisterRequestValidator**
   - Username: 3-50 characters, alphanumeric with underscores/hyphens
   - Email: Valid email format, max 255 characters
   - Password: Min 8 characters, uppercase, lowercase, digit required
   - DisplayName: 1-100 characters

2. **LoginRequestValidator**
   - Username/Email: Required, max 255 characters
   - Password: Required, max 100 characters

3. **SendMessageRequestValidator**
   - ChatId: Required, valid format
   - Content: Required, max 10,000 characters
   - ReplyToId: Optional, max 26 characters

4. **UserPreferenceDtoValidator**
   - Theme: Must be 'light' or 'dark'
   - Language: 2-5 characters
   - MutedChats: Max 1000 items

### Validation Features

- **Automatic Validation**: Validators registered via DI
- **ModelState Integration**: Validation errors in ModelState
- **Consistent Error Responses**: Standardized error format
- **Field-Level Errors**: Detailed validation messages

### Protection Against

- **SQL Injection**: Parameterized queries, input validation
- **XSS (Cross-Site Scripting)**: Input sanitization, output encoding
- **Command Injection**: Input validation, no shell execution
- **Path Traversal**: Path validation, restricted file access
- **Buffer Overflow**: String length validation

## Rate Limiting

### Implementation

NexusTeam implements Redis-based rate limiting to prevent brute force attacks and spam.

**Configuration**:
```json
{
  "RateLimit": {
    "LoginMaxAttempts": 5,
    "LoginWindowSeconds": 300,
    "MessageMaxAttempts": 60,
    "MessageWindowSeconds": 60
  }
}
```

### Rate Limits

**Login Endpoint**:
- Maximum: 5 attempts per 5 minutes per identifier (username/email/IP)
- Returns: HTTP 429 (Too Many Requests)
- Includes: Retry-After header

**Message Sending**:
- Maximum: 60 messages per minute per user
- Applies to: WebSocket message sending
- Prevents: Message flooding and spam

**General API**:
- Configurable per endpoint
- User-based and IP-based limits
- Sliding window algorithm

### Rate Limiting Features

- **Redis-Based**: Fast, distributed rate limiting
- **Graceful Degradation**: Returns true on Redis errors (doesn't block legitimate requests)
- **Retry-After Header**: Tells client when to retry
- **Per-User Limits**: User-specific rate limits
- **Per-IP Limits**: IP-based rate limits (future)

### Protection Against

- **Brute Force Attacks**: Login rate limiting
- **Credential Stuffing**: Account lockout after failed attempts
- **Message Spam**: Message rate limiting
- **API Abuse**: General API rate limiting

## Security Headers

### Implementation

NexusTeam includes security headers middleware that adds security headers to all HTTP responses.

**Headers Added**:

1. **X-Content-Type-Options: nosniff**
   - Prevents MIME-sniffing attacks
   - Forces browsers to respect declared content types

2. **X-Frame-Options: DENY**
   - Prevents clickjacking attacks
   - Blocks page embedding in iframes

3. **X-XSS-Protection: 1; mode=block**
   - Enables XSS filter in older browsers
   - Blocks pages when XSS detected

4. **Referrer-Policy: strict-origin-when-cross-origin**
   - Controls referrer information
   - Limits information leakage

5. **Permissions-Policy: geolocation=(), microphone=(), camera=()**
   - Restricts browser features
   - Prevents unauthorized access to device features

6. **Content-Security-Policy**
   - Restricts resource loading
   - Prevents XSS and injection attacks
   - Configurable per environment

### Configuration

```csharp
// Security headers middleware
app.UseSecurityHeaders();
```

### Protection Against

- **XSS Attacks**: Content-Security-Policy, X-XSS-Protection
- **Clickjacking**: X-Frame-Options
- **MIME-Sniffing**: X-Content-Type-Options
- **Information Leakage**: Referrer-Policy

## CORS Configuration

### Implementation

NexusTeam implements configurable CORS (Cross-Origin Resource Sharing) policies.

**Configuration**:
```json
{
  "Cors": {
    "AllowedOrigins": [
      "http://localhost:5000",
      "https://localhost:5001"
    ],
    "AllowCredentials": true,
    "PolicyName": "NexusTeamCorsPolicy"
  }
}
```

### CORS Features

- **Configurable Origins**: Whitelist of allowed origins
- **Credentials Support**: Allows cookies and authentication headers
- **Named Policy**: Avoids conflicts with framework methods
- **Environment-Specific**: Different policies for dev/prod

### Production Considerations

- **Restrict Origins**: Only allow trusted domains
- **HTTPS Only**: Use HTTPS origins in production
- **No Wildcards**: Avoid wildcard origins in production
- **Credentials**: Only enable if necessary

## WebSocket Security

### Authentication

**Connection Authentication**:
- JWT token required for WebSocket connection
- Token passed as query parameter or in first message
- Token validated before connection established
- Unauthenticated connections rejected

**Message Authentication**:
- User context from authenticated connection
- Message sender validated
- Chat participation verified

### Connection Security

- **WSS in Production**: Encrypted WebSocket connections
- **Origin Validation**: Origin header validation
- **Connection Limits**: Per-user connection limits
- **Heartbeat**: Connection health monitoring

### Message Security

- **Input Validation**: All messages validated
- **Rate Limiting**: Message rate limits
- **Size Limits**: Maximum message size
- **Content Filtering**: Content validation (future)

### Voice Call Security

**Call Signaling**:
- All call messages (requests, answers, signaling) authenticated via WebSocket JWT
- Call initiation requires authenticated connection
- Call requests validated for user identity
- Recipient verification before call forwarding
- Only authorized participants can participate in calls

**Call Data Security**:
- SDP offers/answers transmitted securely via WebSocket (WSS in production)
- ICE candidates exchanged securely
- Audio data transmission (peer-to-peer via WebRTC where applicable)
- Call state synchronized securely between participants

**Call Privacy**:
- Call requests only forwarded to intended recipient
- Call rejection respected immediately
- Call end signals propagated to all participants
- No call data stored on server (signaling only)
